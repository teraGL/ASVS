# V9 Self-contained токени

## Мета контролю

Поняття self-contained токена згадується в оригінальному стандарті RFC 6749 OAuth 2.0 від 2012 року. Йдеться про токен, що містить дані або атрибути (claims), на підставі яких сервіс-отримувач ухвалює рішення з безпеки. Такий токен слід відрізняти від простого токена, що містить лише ідентифікатор і використовується сервісом-отримувачем для локального отримання даних. Найпоширенішими прикладами самодостатніх токенів є JSON Web Token (JWTs) та твердження SAML.

Використання self-contained токенів стало надзвичайно поширеним, зокрема й поза межами OAuth та OIDC. Водночас, безпека цього механізму ґрунтується на здатності перевіряти цілісність токена та забезпечувати його дійсність у конкретному контексті використання. Процес такої перевірки має багато підводних каменів, і в цьому розділі наведено конкретні вимоги до механізмів, які застосунки повинні реалізувати для їх запобігання.

## V9.1 Джерело токена та його цілісність

Цей підрозділ містить вимоги, спрямовані на забезпечення того, що токен був створений довіреною стороною та не був підробленим.

| # | Опис | Рівень |
| :---: | :--- | :---: |
| **9.1.1** | Перевірити, що self-contained токени перед прийняттям їхнього вмісту проходять перевірку за допомогою цифрового підпису або MAC з метою захисту від підробки. | 1 |
| **9.1.2** | Перевірити, що для створення та перевірки самодостатніх токенів у межах конкретного контексту дозволено використовувати лише алгоритми з дозволеного переліку (allowlist). Такий перелік повинен містити дозволені алгоритми, бажано лише симетричні або лише асиметричні, і не повинен включати алгоритм 'None'. Якщо необхідно підтримувати як симетричні, так і асиметричні алгоритми, мають бути реалізовані додаткові засоби контролю для запобігання key confusion атак. | 1 |
| **9.1.3** | Перевірити, що ключовий матеріал, який використовується для перевірки self-contained токенів, походить із довірених, попередньо налаштованих джерел, визначених для видавця (issuer) токена, що унеможливлює вказування зловмисниками недовірених джерел і ключів. Для JWT та інших структур JWS, заголовки, зокрема 'jku', 'x5u' та 'jwk', повинні перевірятися на відповідність дозволеному переліку (allowlist) довірених джерел. | 1 |

## V9.2 Вміст токена

Перш ніж ухвалювати рішення з безпеки на основі вмісту self-contained токена, необхідно перевірити, що токен подано в межах строку його дії, а також що він призначений для використання сервісом-отримувачем і саме з тією метою, з якою його було надано. Це допомагає уникнути небезпечного перехресного використання токенів між різними сервісами або використання різних типів токенів одного й того самого видавця (issuer) не за призначенням.

Окремі вимоги для OAuth та OIDC наведено у відповідному розділі.

| # | Опис | Рівень |
| :---: | :--- | :---: |
| **9.2.1** | Перевірити, що у разі наявності в даних токена періоду дії, токен і його вміст приймаються лише тоді, коли час перевірки перебуває в межах цього періоду дії. Наприклад, для JWT повинні перевірятися атрибути 'nbf' та 'exp'. | 1 |
| **9.2.2** | Перевірити, що сервіс, який отримує токен, перевіряє чи токен має коректний тип і призначений для відповідної мети, перш ніж приймати його вміст. Наприклад, Access Tokens можуть використовуватися лише для рішень з авторизації, а ID Tokens лише для підтвердження автентифікації користувача. | 2 |
| **9.2.3** | Перевірити, що сервіс приймає лише ті токени, які призначені для використання саме цим сервісом (audience). Для JWT це може бути реалізовано шляхом перевірки атрибуту 'aud' на відповідність дозволеному переліку (allowlist), визначеному в сервісі. | 2 |
| **9.2.4** | Перевірити, що якщо видавець токена використовує один і той самий приватний ключ для видачі токенів різним адресатам (audiences), видані токени містять обмеження за адресатом, яке однозначно ідентифікує призначеного адресата. Це запобігає повторному використанню токена для непередбаченого адресата. Якщо ідентифікатор адресата надається динамічно, видавець токена повинен перевіряти такі значення, щоб переконатися, що це не призводить до підміни адресата (audience impersonation) | 2 |
