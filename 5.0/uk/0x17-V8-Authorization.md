# V8 Авторизація

## Мета контролю

Авторизація забезпечує, що доступ надається лише дозволеним споживачам (користувачам, серверам та іншим клієнтам). Для забезпечення дотримання принципу найменших привілеїв (POLP), перевірені застосунки повинні відповідати наступним високорівневим вимогам:

* Документувати правила авторизації, включно з чинниками, що впливають на прийняття рішень, та контекстами середовища.
* Споживачі повинні мати доступ лише до тих ресурсів, які дозволені відповідно до їхніх визначених повноважень.

## V8.1 Документація з авторизації

Повна та всебічна документація з авторизації є критично важливою для забезпечення послідовного застосування рішень щодо безпеки, можливості їх аудиту та відповідності політикам організації. Це знижує ризик несанкціонованого доступу, роблячи вимоги безпеки зрозумілими та такими, що підлягають реалізації для розробників, адміністраторів і тестувальників.

| # | Опис | Рівень |
| :---: | :--- | :---: |
| **8.1.1** | Перевірити, що документація з авторизації визначає правила обмеження доступу на функціональному рівні та до конкретних даних на основі дозволів споживача та атрибутів ресурсу. | 1 |
| **8.1.2** | Перевірити, що документація з авторизації визначає правила обмеження доступу на рівні полів (як для читання, так і для запису) на основі дозволів споживача та атрибутів ресурсу. Зауважте, що ці правила можуть залежати від інших значень атрибутів відповідного об’єкта даних, таких як стан або статус. | 2 |
| **8.1.3** | Перевірити, що документація застосунку визначає середовищні та контекстуальні атрибути (включно, але не обмежуючись часом доби, розташуванням користувача, IP-адресою або пристроєм), які використовуються у застосунку для прийняття рішень щодо безпеки, зокрема в контексті автентифікації та авторизації. | 3 |
| **8.1.4** | Перевірити, що документація з автентифікації та авторизації визначає, яким чином середовищні та контекстуальні фактори враховуються під час прийняття рішень, на додаток до авторизації на рівні функцій, даних і полів. Документація повинна містити опис оцінюваних атрибутів, порогових значень ризику та відповідних дій (наприклад, дозволити, запросити додаткову перевірку, відмовити, підвищити рівень автентифікації). | 3 |

## V8.2 Загальний дизайн авторизації

Впровадження гранулярних контролів авторизації на рівнях функцій, даних і полів забезпечує, що споживачі мають доступ лише до тих ресурсів і операцій, які їм явно надані.

| # | Опис | Рівень |
| :---: | :--- | :---: |
| **8.2.1** | Перевірити, що застосунок забезпечує обмеження доступу на функціональному рівні лише для споживачів з явними дозволами. | 1 |
| **8.2.2** | Перевірити, що застосунок забезпечує обмеження доступу до конкретних даних лише для споживачів з явними дозволами на відповідні елементи даних, щоб запобігти вразливостям типу insecure direct object reference (IDOR) та broken object level authorization (BOLA). | 1 |
| **8.2.3** | Перевірити, що застосунок забезпечує обмеження доступу на рівні полів лише для споживачів із явними дозволами на конкретні поля, щоб запобігти вразливостям типу broken object property level authorization (BOPLA). | 2 |
| **8.2.4** | Перевірити, що адаптивні заходи безпеки, засновані на середовищних та контекстуальних атрибутах споживача (наприклад, час доби, місцезнаходження, IP-адреса або пристрій), реалізовані для прийняття рішень щодо автентифікації та авторизації відповідно до документації застосунку. Ці заходи мають застосовуватися як під час ініціації нової сесії, так і під час існуючої. | 3 |

## V8.3 Авторизація на рівні операцій

Негайне застосування змін у авторизації на відповідному рівні архітектури застосунку є критично важливим для запобігання несанкціонованим діям, особливо в динамічних середовищах.

| # | Опис | Рівень |
| :---: | :--- | :---: |
| **8.3.1** | Перевірити, що застосунок забезпечує дотримання правил авторизації на довіреному рівні сервісів і не покладається на контролі, які може змінити недовірений споживач, такі як клієнтський JavaScript. | 1 |
| **8.3.2** | Перевірити, що зміни значень, на основі яких приймаються рішення щодо авторизації, застосовуються негайно. У випадках, коли негайне застосування змін неможливе (наприклад, при використанні даних у самодостатніх токенах), повинні бути впроваджені компенсувальні механізми, які повідомляють про спробу дії споживача після втрати ним авторизації та скасовують цю зміну. Зверніть увагу, що така альтернатива не усуває ризик витоку інформації. | 3 |
| **8.3.3** | Перевірити, що доступ до об’єкта базується на дозволах вихідного суб’єкта (наприклад, споживача), а не на дозволах будь-якого посередника чи сервісу, який діє від його імені. Наприклад, якщо споживач виконує виклик веб-сервісу, використовуючи самодостатній токен для автентифікації, і цей сервіс далі запитує дані в іншого сервісу, то другий сервіс повинен використовувати токен споживача, а не машинний токен першого сервісу, для прийняття рішень щодо дозволів. | 3 |

## V8.4 Інші аспекти авторизації

Додаткові аспекти авторизації, особливо для адміністративних інтерфейсів та multi-tenant середовищ, допомагають запобігти несанкціонованому доступу.

| # | Опис | Рівень |
| :---: | :--- | :---: |
| **8.4.1** | Перевірити, що multi-tenant застосунки використовують механізми контролю cross-tenant, які гарантують, що операції споживачів ніколи не впливатимуть на tenants, з якими у них немає дозволів на взаємодію. | 2 |
| **8.4.2** | Перевірити, що доступ до адміністративних інтерфейсів реалізує багаторівневі заходи безпеки, включаючи постійну верифікацію ідентичності споживача, оцінку безпекового стану пристрою та контекстний аналіз ризиків, забезпечуючи, що мережеве розташування або довірені кінцеві точки не є єдиними факторами для авторизації, хоча й можуть знижувати ймовірність несанкціонованого доступу. | 3 |
